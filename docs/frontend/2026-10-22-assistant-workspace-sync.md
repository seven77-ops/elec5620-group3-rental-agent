# Conversation, preferences and recommendations share one workspace

The user chose to consolidate the separate preferences navigation item into the chat page's “我的租房需求” drawer. The real-listings sidebar now contains the assistant, recommendations, contracts and aftercare. The complete manual preferences route remains available from the drawer's secondary settings link; no existing saved fields are removed. Recommendation-page requirement actions lead back into chat. The redundant progress page was removed; old overview links redirect to the assistant.

The drawer is prefilled from conversation-only requirements or the user's valid confirmed profile. It shows pending versus synchronized state, allows editing the core housing/budget/occupancy/rental-mode fields, and exposes an explicit “确认并同步需求” action. Preparation displays the complete profile summary, including inherited dates, commute, facilities and weights; only the following confirmation writes the Agent1 version and generates the Agent2 report. Cancel leaves the saved case unchanged. A valid pending AI proposal supplies the base profile, so editing core fields does not discard other AI-proposed conditions such as lease length.

Both in-message and drawer confirmations use the same Agent1/Agent2 workflow. Conversation state and the last report filters are refreshed after apply. A visible status strip links to the recommendation page. Draft edits cannot overwrite a newer conversation silently; stale conversation revisions and profile fingerprints are rejected.

Each chat property card has an explicit candidate-save action. It saves only a displayed, unchanged catalogue card that satisfies the current confirmed profile, composing real evaluation and selection atomically. Out-of-profile, stale, unconfirmed and cross-case requests fail without partial case changes. The same case.selection snapshot appears in recommendations and survives reload. Saving a different candidate explicitly replaces the existing current candidate. Saving a public advertisement does not mark availability verified or make a real listing contract-ready.

Implementation adds bounded `/conversations/{id}/proposals` and `/conversations/{id}/selections` endpoints under the existing assistant prefix. They use strict schemas, request receipts, revision/fingerprint checks and existing adapter transactions; neither endpoint calls an external model. Selection child request IDs are hashed to fit the public 80-character limit.
