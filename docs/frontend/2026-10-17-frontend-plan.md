# ELEC5620 Group 3 前端方案

版本：v0.1 讨论稿
日期：2026-10-17（Australia/Sydney）
适用范围：统一租客界面、本地 Python 接口及课程演示
依据：[统一前端实施交接方案](./2026-10-17-frontend-handoff.md)

本方案将交接文档中的业务要求落实到页面结构、交互、视觉和开发顺序，便于后续修改。当前内容是拟实施设计，不代表页面、接口或验收已经完成。业务契约、规则和详细验收条件沿用交接文档；调整本方案时，应同步检查是否影响原有门禁。

## 1. 产品定位与范围

采用面向学生租客的“租房流程工作台”。用户在每个阶段都能看清当前状态、结果依据和下一步操作。

主流程：

```text
编辑租房偏好 → 确认偏好版本 → 生成推荐 → 明确选择房源
                                         ↓
独立同意合同处理 → 上传合成合同 → 查看复核及处理待办
                                         ↓
补齐并确认租约资料 → 退租计划、任务、押金与可选提醒
```

已有租约的用户可以通过“直接填写租约资料”进入租后服务。

### 1.1 能力边界

| 模块 | 本次页面能力 | 接入原则 |
| --- | --- | --- |
| Agent 1 | 可编辑偏好、摘要、草稿和明确确认 | 标注“模拟 Agent 1 输入”，保留未来适配入口 |
| Agent 2 | 推荐、资格分类、依据、版本比较、明确选房 | 调用原 Python 实现，不在前端重写评分 |
| Agent 3 | 独立同意、合成合同上传、复核、修正、问题清单 | 保留同意、复核版本、人工决定及重试门禁 |
| Agent 4 | 确认租约资料、计划、任务、改期、押金、提醒 | 使用实际 command Schema 和原状态机 |

默认关闭外部模型调用，使用合成数据。真实房源抓取、地图导航、签约、付款、对外发送和生产账号体系不在本次范围内。

### 1.2 方案选择

| 方案 | 优点 | 取舍 |
| --- | --- | --- |
| 流程工作台，推荐 | 阶段清楚，方便回看证据、版本和历史结果 | 需要统一管理案例及阶段状态 |
| 全屏分步向导 | 首次操作容易理解 | 回头比较房源或修正合同较麻烦 |
| 对话式界面 | 接近助手体验 | 当前 Agent 1 为模拟输入，核心操作仍依赖表单和证据视图 |

## 2. 信息架构与导航

桌面采用左侧阶段导航、主内容区和按需打开的证据抽屉。导航用租客能够理解的名称，技术标识放进“演示与证据”区域。

以下为拟定前端路由，不表示现有接口已经存在。

| 页面 | 拟定路由 | 页面职责 |
| --- | --- | --- |
| 我的进度 | `/cases/:caseId/overview` | 当前阶段、待办、最近有效结果和继续入口 |
| 租房偏好 | `/cases/:caseId/preferences` | 编辑、保存、确认和查看偏好版本 |
| 房源推荐 | `/cases/:caseId/recommendations` | 推荐、资格、依据、比较和选房 |
| 合同复核 | `/cases/:caseId/contract` | 同意、上传、复核结果、修正和问题清单 |
| 租后服务 | `/cases/:caseId/aftercare` | 租约确认、退租计划、任务、押金和提醒 |
| 演示操作员 | `/operator` | 由服务器授权的本地演示人工决定 |

根页面提供“新建演示案例”和“继续上次案例”。历史结果可查看，后续写操作由服务端检查前置条件。进入操作员路由本身不授予权限。

## 3. 页面设计与主要交互

### 3.1 我的进度

页面显示当前案例和阶段、一条主要的“继续操作”按钮、待用户处理事项，以及最近有效结果。

阶段使用“待填写、待确认、处理中、待人工复核、已完成当前步骤”等实际状态。合同复核完成不表示已签约，导航也不能因此自动显示整个租房流程完成。

顶部显示“合成数据演示”。快照、模拟选择、合同规则参考及实际操作时间在对应区域分别说明。

### 3.2 租房偏好

桌面使用左侧分组表单和右侧摘要；窄屏改为上下排列。

| 分组 | 主要字段 |
| --- | --- |
| 预算与居住方式 | 期望及最高周预算、计价对象、账单范围、硬上限、人数、租赁方式 |
| 通勤 | 目的地、到达时间、交通方式、期望及最长时间、硬上限 |
| 入住与租期 | 入住日期窗口、租期 |
| 硬要求与偏好 | 必须满足的设施、软偏好，以及通勤、费用、居住、设施四维权重 |

具体字段取值以 RentalProfile Schema 和后端校验为准。四维权重使用滑块搭配数值输入；有效归一化权重以服务端结果为准。

右侧摘要用自然语言呈现将被批准的条件，注明模拟样例来源。保存、确认和评估为三个独立操作：

1. “保存草稿”保存当前修订，不产生用户确认。
2. “确认当前偏好”展示准确摘要，确认精确草稿修订和正文指纹。
3. “生成推荐”只使用服务端已保存的确认版本。

再次编辑后显示“有未确认修改”；原确认版本和旧推荐仍可查看。必填缺失或条件冲突时，字段旁显示可操作的说明，并阻止不符合条件的提交。

### 3.3 房源推荐

顶部显示当前偏好摘要、报告绑定版本、快照及评估时间，并提供“修改偏好”和历史报告入口。

默认展示最多五条推荐，另设“全部合格、待确认、已排除、重复记录”分类。分类数量使用实际响应。零匹配显示原因和返回偏好的入口，不自动放宽条件。

每条推荐呈现：

- 房源标识、排名、偏好匹配分。
- 可比周费用、计价对象、账单范围、通勤。
- 推荐理由和主要取舍。
- “查看推荐依据”和“选择此房源”。

“查看推荐依据”打开证据抽屉，包含硬条件检查、四维分项、来源引用、观察时间和输入快照。没有正式分数的候选显示“未评分”，不填零分、不加入排名。

“选择此房源”先展示选择摘要；用户明确确认后，由后端复核本批次资格和证据时效，生成真实 SelectedListingEvidence。成功后提供“继续合同复核”和“下载选房证据包”。下载不表示对外发送。

#### 推荐页布局示意

```text
┌─────────────────────────────────────────────────────────┐
│ 租房助手                 当前案例       合成数据演示      │
├───────────┬─────────────────────────────────────────────┤
│ 我的进度  │ 房源推荐                       偏好版本 v1  │
│ 租房偏好  │ 根据已确认偏好生成                           │
│ 房源推荐  ├─────────────────────────────────────────────┤
│ 合同复核  │ 当前偏好摘要                     修改偏好    │
│ 租后服务  ├─────────────────────────────────────────────┤
│           │ 推荐｜全部合格｜待确认｜已排除｜重复记录      │
│           │                                             │

│           │     周费用 · 通勤 · 计价对象                │
```

版本比较使用表格显示偏好变化、排名和分数前后值、四维贡献及变化原因。先重新确认偏好，再调用后端比较；不符合相同搜索、数据快照等比较条件时，提示重新评估，不推测比较结果。

### 3.4 合同复核

页面顺序为“已选房源摘要 → 独立合同处理同意 → 文件上传 → 复核结果”。独立审查入口需明确说明缺少选房交叉核对。

同意区展示处理目的和范围。只有创建服务器同意记录成功后，才开放文件选择、读取及上传。撤销后停止后续处理；已保存文件的处理方式由服务端生命周期规则明确，页面不将撤销描述成已经完成删除。

服务端必须在解析上传内容前验证有效同意，不能只依赖前端禁用控件。支持 TXT、DOCX、PDF，最多 2,000,000 字节，PDF 最多 10 页。扫描 PDF 缺少 OCR 能力时，提示提供文字版或更清晰副本。

复核结果在桌面使用左右分栏：左侧为状态、字段和发现项，右侧为受控原文片段。点击来源定位对应引文。窄屏改用全屏证据面板，原文按文本渲染。

| 后端状态 | 页面表达及允许操作 |
| --- | --- |
| Reviewed | 复核完成；展示结果范围，不表述为签约批准 |
| Awaiting Human Review | 等待人工复核；展示需处理事项 |
| Awaiting Resubmission | 需要补充或重新提交，并说明原因 |
| Degraded Summary Only | 当前仅能提供有限摘要，列出缺少的能力或信息 |
| Questions Ready | 问题清单已准备，尚未发送 |

字段修正生成新复核版本，并使旧问题失效。没有发现项时不补造问题。生成问题须符合后端状态条件；租客页面不提供人工放行按钮。

上传重试保留同一逻辑请求的 request_id、文件内容、选房包、参考日期和同意上下文。同 ID 改内容时展示明确冲突，不自动换 ID 掩盖冲突。

### 3.5 租后服务

先展示“确认租约资料”表单。从合同预填的字段逐项标明 review_id、版本和来源引用，允许租客修改。用户补齐并确认 M4 必要字段后，服务端按实际契约创建 TenancyRecord。

确认后分为三个主要视图：

| 视图 | 内容及交互 |
| --- | --- |
| 退租计划 | 退租日期、计划生成与确认、任务编辑及完成、证据、未决澄清和 evidence_gaps |
| 押金跟进 | 原始业务状态、时间线、reported_claim、待审核事项、跟进草稿和租客确认入口 |
| 本地提醒 | 默认关闭；显式开启后显示本地收件箱、提醒状态及适用范围 |

改期采用“提交提案 → 查看影响 → 明确确认”。确认前保留原计划，确认后按原逻辑更新并保留完成与证据记录。

押金金额按 AUD 整数分传输和保存，界面格式化为元。扣款记录不表示租客接受扣款；关闭或撤回需要明确确认。

提醒开启后，活跃页面可每 30 秒调用既有 poll_reminders。每次新轮询是新操作，失败重试复用原请求，并遵守版本、去重和服务端演示时钟。页面关闭后不保证提醒投递。

### 3.6 演示操作员

通过单独入口展示待审核列表、相关证据和原模块允许的决定操作。明确标注“本地演示操作员”，服务器使用配置的允许列表授权。

浏览器提交角色字符串不能获得权限。annotate、return、hold、refer 等决定按实际含义展示，不统一呈现为“审核通过”。

## 4. 视觉与响应式

采用浅色背景、深蓝主色、少量青绿色强调。内容以表单、列表、证据和时间线为主，通过间距和文字层级组织页面。

以下为拟定设计值，实施时结合实际页面和对比度检查调整。

| 项目 | 初始设计值 |
| --- | --- |
| 页面背景 | `#F5F7FA` |
| 内容背景 | `#FFFFFF` |
| 正文 | `#172B4D` |
| 主操作 | `#174EA6` |
| 辅助强调 | `#087F8C` |
| 间距基准 | 8px；常用 16、24、32px |
| 圆角 | 8–12px |
| 正文字号 | 14–16px |
| 页面标题 | 26–28px |
| 桌面侧栏 | 约 208px |

房源内容以费用、通勤和解释为中心。图片仅在有明确素材时使用，并标注演示属性，不作为真实房源证据。

| 检查宽度 | 布局要求 |
| --- | --- |
| 1440px | 固定侧栏，偏好与合同支持双栏 |
| 768px | 收起辅助栏，表单按空间减少列数 |
| 360px | 单栏、折叠菜单，证据使用全屏面板 |

关键控件有标签，支持键盘操作和清晰焦点。弹窗关闭后恢复触发位置焦点；加载、错误和审核状态有文字说明。长地址、引用、合同文本和错误信息可换行，比较表允许局部横向滚动，不撑破整页。

## 5. 技术与组件组织

沿用交接文档的 React、TypeScript、Vite、Ant Design，连接 FastAPI 和本地 SQLite。依赖版本在实施时按模板兼容性核对，并提交 lockfile。

Ant Design 用于表单、导航、列表、表格、抽屉、弹窗、提示和时间线，通过统一主题配置管理颜色、间距和圆角。

```text
frontend/src/
  app/                    路由、导航、布局、页面错误边界
  features/
    overview/             当前进度与待办
    preferences/          草稿、摘要和版本确认
    recommendations/      推荐、比较、证据与选房
    contract/             同意、上传、复核及修正
    aftercare/            租约资料、计划、押金及提醒
    operator/             本地演示人工决定
  components/             跨业务复用组件
  api/                    HTTP客户端、DTO、错误转换
  state/                  当前案例引用及界面状态
  styles/                 全局样式与主题配置

server/app/
  routes/                 HTTP输入输出及边界校验
  adapters/               各Agent调用包装
  repository/             案例、确认版本、关联和幂等记录
  settings.py             数据路径、身份、时钟及模型配置
```

通用组件优先包括：案例与模式提示、状态说明、确认摘要、版本选择器、证据抽屉、可恢复错误提示和带请求状态的提交按钮。业务校验仍由服务端负责。

## 6. 状态、数据与异常规则

### 6.1 状态归属

| 数据 | 保存位置 | 页面处理 |
| --- | --- | --- |
| 案例、草稿修订、不可变确认版本 | 服务端协调层 | 打开案例时恢复，提交带修订约束 |
| 数据快照、推荐报告、选房包 | 服务端 | 页面与下载均读取保存结果 |
| 合同同意、文件引用、复核版本和收据 | 服务端及 Agent 3 原存储 | 上传及后续操作绑定正确版本和同意 |
| 租后服务案件及版本 | Agent 4 原存储，协调层保存映射 | 写入遵守 expected_version 和原命令契约 |
| 折叠状态、标签页等界面偏好 | 前端状态；必要时 localStorage | 不作为业务完成或授权依据 |

caseId、searchId、profileVersion、taskId 和各模块业务 ID 分别保存与映射，不互相替代。

新结果必须核对案例、搜索、偏好版本及指纹、数据快照和批次绑定。旧响应可以保留为历史，不能覆盖当前版本。刷新后恢复服务器保存的有效状态。

### 6.2 异常与恢复

| 情况 | 页面行为 |
| --- | --- |
| 字段格式错误或缺项 | 定位字段，说明需要补充什么 |
| 无合格候选 | 展示有效空结果及原因，允许返回修改偏好 |
| 版本冲突 | 保留用户输入，提示读取最新版本并重新核对 |
| 网络超时 | 保留旧结果及原请求身份，允许按原输入重试 |
| 同 ID 不同输入 | 显示重复输入冲突，要求明确发起新操作 |
| 待人工复核或部分报告 | 明确状态和可用操作，不转成普通成功 |
| 文件解析失败或能力不足 | 说明可接受的替代文件，不显示解析成功 |

HTTP 错误沿用 code、message、request_id，可附字段错误；页面不显示服务器绝对路径和堆栈。

## 7. 接口接入与演示时钟

接口沿用交接文档第 6 节的拟定 `/api/v1` 路由。最终请求、响应及错误示例在 server README 和 OpenAPI 中记录。

接入顺序为案例与偏好、推荐与选房、合同同意与复核、租后服务命令。HTTP 层只包装现有业务函数，浏览器不能提交任意服务器文件路径。

| 时间 | 展示及处理方式 |
| --- | --- |
| 房源评估快照 | 固定合成场景为 `2026-09-17T09:00:00+10:00` |
| 模拟选房业务时间 | 回放成功路径为 `2026-09-17T10:00:00+10:00`，明确标注模拟 |
| 合同规则参考日期 | 合成示例为 `2026-10-15` |
| M4 操作时间 | 使用其原样例和统一服务端演示时钟，保持单调 |
| 实际操作记录时间 | 单独记录和展示，不替换来源观察时间 |

以实际当前时点检查旧房源时，应允许返回过期结果并要求新快照，不修改原证据时间。

## 8. 实施批次与交付标准

| 批次 | 工作范围 | 可检查的交付结果 |
| --- | --- | --- |
| 第一批：基础与偏好 | 统一布局、案例保存恢复、模拟偏好编辑、确认版本、演示时钟 | 刷新可恢复；未确认不能评估；修改产生新草稿 |
| 第二批：推荐到合同闭环 | 原模块推荐、依据、比较、选房、独立同意、上传及 receive | 正常和合同冲突路径均可实际操作；保存结果与下载一致 |
| 第三批：租后与人工决定 | 租约资料确认、计划任务、改期、押金、操作员、提醒 | 不自动创建已确认租约；租客不能执行操作员决定 |
| 第四批：验收与演示 | 响应式、键盘、异常恢复、浏览器流程、截图及验证记录 | 360/768/1440px可用；实际结果对应交接文档 F01–F20 |

首个演示闭环覆盖“确认偏好 → 推荐 → 明确选房 → 独立合同同意 → 合同复核”。同步验证无匹配、未同意、版本变化、重复请求和合同冲突。

前端执行类型检查与构建，关键交互和 API 边界重点验证确认、绑定、重试、上传、权限及真实模块调用。现有 Agent 测试按实施时仓库实际内容运行并记录，不把预期数量填写成测试通过结果。

验收记录另存 `docs/frontend/verification.md`，包括实际命令、预期与实际、截图及复现方法。Stage 1 的量化响应和用户测试要求需另行实际测量。
