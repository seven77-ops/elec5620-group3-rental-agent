# 租约资料接续、报修连续对话和租后待办

日期：2026-10-22。沿用真实模式租后服务页 `/cases/{case_id}/aftercare`，未新增独立进度页。

## 使用方式

1. **租约资料接入**：点击“查看租约来源”，对照已有资料与来源字段，选择要接入的地址、联系人、起止日期等。确认来源是自己的实际租约后，再确认接入。来源可能是已确认租后租约，或已保存、仍关联当前候选和跟进版本的未签署草稿；草稿不自动表示已入住。
2. **同一条报修连续处理**：聊天整理问题后，可以说“写得客气一点”“中介回复说明天来修”“已经修好了”。待确认的草稿改写后仍需确认；保存后的后续动作更新同一条报修。页面“记录后续”“调整邮件语气”也可操作，记录用户原话、处理状态及更新时间。
3. **待办直达**：顶部汇总尚待联系/处理的报修、报价或日期待核对的服务、已记录的后续预约、预计退租事项和必要的联系人补充。默认显示前五项，更多事项可展开。点击可切换到正确页面并聚焦具体报修或服务卡片。解决报修后，该项从待办消失。未接入定时通知。

报修卡片“继续聊这条报修”只预填问题标识与名称，不自动发送。用户仍需选择本轮外部 AI 同意。AI 上下文含本案例问题标识、用户描述和状态、当前聚焦问题或待确认草稿；住址和联系人邮箱/电话继续留在本地资料中，不因已保存而自动进入模型上下文。

## 数据与确认边界

- `LivingProfile` 增加 `lease_start_date`、`lease_end_date`，与用户预计搬出的 `move_out_date` 区分。旧记录读取补为空；旧客户端保存时省略新日期字段，会保留已存日期；明确传 null 才会清空。
- `GET .../living-services/tenancy-source` 只读返回来源 ID、版本、token、是否仍有效、来源值与已有值。相同住址的当前草稿可补充已确认租后租约缺少的联系人/租期；界面分别保留两类来源的版本标签及未签署来源提示。
- `POST .../living-services/tenancy-import` 需要 `request_id`、`expected_version`、`confirmed:true`、`actual_tenancy_confirmed:true`、`source_token` 和所选 `fields`。后端重新读取来源、检查版本及案例归属；来源中空值不提供、不覆盖现有值。只合并所选字段并保存 `tenancy_source` 元数据。
- 地址发生变化时明确提醒核对是否换住处。原供应商、报修、服务及附件保留，不会静默迁移或清空。
- 报修更新可包含 status、用户原话 note、邮件语气 email_tone；使用原有带确认和版本的写入接口。记录中的邮件事实、收件人和问题 ID 保持不变，语气使用受限措辞模板调整；不生成虚构回复或预约日期。
- 聊天保存 durable repair focus。提案确认后记录对应 repair ID；下轮读取相同记录，多个问题且指代不明时询问具体哪一条。不能凭模型返回任意 ID 更新未被用户指明的其他问题。未确认草稿改写会替代旧提案，旧按钮标记已被后续修改替代，不能再次应用。
- 所有同步/报修更新继续执行案例归属、幂等回执和版本冲突检查。邮件仍为未发送草稿，服务预约仍为用户记录。
